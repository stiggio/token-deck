## 0. Verdict in one paragraph

The firmware is alive (enumerates, answers GET_REPORT 0, emits key events — `PROBE/NOTES.md:47-49`, user report), so this is not the vendor-described failed-firmware state ("completely no display and no response", HSV293 guide, forum tid=22). The single documented effect of the frame we sent last at 20:10, `CRT\0\0CLE\0\0DC`, is "Disconnects and clears all display" (vendor Python API reference). The 20:10 session is the only one that ever sent DC and the only one followed by a black panel; every earlier session closed silently and the panel went back to the VSD logo **[observed by us]**. The most economical reading is therefore: DC blanked the panel and this clone does not redraw anything (no logo fallback, no reboot) until a host paints or power is cycled. Whether the 20:10 LOG write also replaced the boot image (correctly, or with something unrenderable) is undetermined and is exactly what the 22:49 solid-lime LOG write (closed without DC) will tell once the user looks now and after a replug. Note our own `PROBE/NOTES.md:17` asserts DC makes "the device fall back to its stored logo"; no source says that, and the 20:10 observation contradicts it — treat that line as wrong until a controlled DC test says otherwise.

## 1. Answers

### Q1 — What does the device do on `CLE\0\0DC`?

- **[documented]** Vendor Python API: `disconnected()` = "Disconnects and clears all display."; `close()` = "Closes device connection and clears all display." (CN "断开连接并清除所有显示。") — https://creator.key123.vip/en/python/api_references.html , https://creator.key123.vip/python/api_references.html . Same comment in code: `SDK Python-SDK/src/StreamDock/Devices/StreamDock.py` lines 285-287 ("# Disconnect and clear all displays"). The C++ header says only "Disconnect the device or mark it as disconnected." (`SDK CPP-SDK/src/DeviceInfo/streamdock.h:105`). No vendor page says what the panel shows afterwards or whether a reconnect/power cycle is needed.
- **[documented, binary]** `transport_disconnected` enqueues exactly one frame, the 12-byte literal `CRT\0\0CLE\0\0DC` (rodata 0x1fcea), report-ID 0 prepended, zero-padded to 1025, no read, no HAN/LIG/STP with it; `transport_destroy` sends nothing (stops the sender thread, 2 s helper sleep, `hid_close`) — `N3R/libtransport_bin/full.asm` 0x16920 (Transport::disconnected), 0xfce0, 0xf890, 0x13540, 0x133a0. Verified on both the Apr–Jun 2026 and Sept 2026 builds of libtransport.so.
- **[documented]** The vendor Python SDK sends DC only on an intentional close while the device is present (`StreamDock.py:256-263`); the C++ examples never call `disconnected()`; libtransport's `disconnected` is reachable only through `transport_disconnected`.
- **[observed by others]** N4 Pro (different device, has a device-stored standby logo): sending `transport_disconnected()` when Stream Deck closes makes the N4 Pro "return to its standalone screen" (physically confirmed); quitting without the notice "can leave the last image visible for tens of seconds before the device returns to standby" — https://github.com/restarea92/hellgato/releases/tag/v0.1.2 . Not transferable to this N3 clone without a test.
- **[observed by others]** 293: collaborator Heart-State, "The background image is stored in the device, so it can still be displayed when the program is closed." — https://github.com/MiraboxSpace/StreamDock-Device-SDK/issues/17 . Says nothing about DC.
- **[observed by others]** Companion, mirajazz/OpenDeck (opendeck-akp03, which lists TreasLin N3 5548:1001), ajazz-sdk and DeckBridge all send CLE DC on a clean close; mirajazz/ajazz/DeckBridge follow it with HAN (sleep) — https://github.com/bitfocus/companion-surface-mirabox-stream-dock/blob/main/src/streamdock.ts , https://docs.rs/crate/mirajazz/latest/source/src/device.rs (shutdown()), `N3R/akp03/device.rs:67-71`. None of their 85 issue titles reports a black panel or lost logo after disconnect; the only persistent-blank report in those trackers is a Fifine D6, not after DC. MelvinTo's N3 code skips DC by default and its skill file says that without the notice "images persist on the device after the CLI exits" (`N3R/melvin_skill_n3.md:77-78`).
- **[observed by others]** Host silence has its own effects on this firmware family: N3 "rebooting every minute or so" while held without CONNECT, fixed by a 15 s CONNECT keep-alive — https://github.com/4ndv/opendeck-akp03/issues/44 and PR #45; V3.293N3 "stops repainting after a period of silence and only recovers on a USB replug" (`N3R/melvin_README.md:39-41`).
- **[observed by us]** Silent close (handshake + BAT tiles, no DC) → panel returned to the VSD logo, several times. 20:10 (LOG, STP, 5 s, DC, close) → "just black … screens are 100% empty", keys still work, no VSD (user report; `PROBE/NOTES.md:44-56`).
- **[inferred]** DC blanks the key LCD/panel and does not itself redisplay the stored boot image on this clone; the cleared state persists until a host paints (DIS + image + STP) or power is cycled. The VSD return after silent closes is a different mechanism (most plausibly the host-silence reboot of #44, or an idle fallback), which a DC-terminated session apparently does not trigger.
- **[unknown]** Whether a power cycle after DC shows the boot image; whether DC touches the backlight (mirajazz adding HAN after DC suggests it does not).

### Q2 — Does the LOG image persist across a power cycle, and what are the constraints?

- **[documented]** `setBackgroundImgFile()` "Set startup background image, writes to the device's ROM: Slower write speed; But remains after restart;" vs `setKeyImgFile()` "writes to the device's RAM … lost after power off" — `SDK CPP-SDK/README.md` §4.4 lines 316-323; §5.1 line 344 "Set startup logo to a static image". CN: "设置开机背景图，写入的是设备的 ROM … 但重启后仍然保留" (`SDK CPP-SDK/README_CN.md:314-316`). Generic to "new platform" devices (N3 listed), not N3-specific.
- **[documented]** Consumer boot-logo tutorial: "The boot logo is the image shown on your StreamDock device when it starts up."; "After the upload is complete, restart or reconnect the device to check the new boot logo."; "Resetting the device will not restore the default boot logo."; wrong resolution → "the upload may fail, or the progress bar may get stuck." — https://mirabox.net/blogs/tutorial/how-to-replace-the-boot-logo-on-streamdock (no model named; 800×480 is an example). VSD Craft's Device tab has "Replace the boot logo" — https://www.vsdinside.com/blogs/tutorial/vsd-craft-system-settings .
- **[documented, binary]** LOG frame = `CRT\0\0LOG` + u32be length + constant `0x01` at byte 12 (no device-type branch), JPEG in 1024-byte payload chunks (1025 with report-ID 0, zero-padded); after the last chunk one `hid_read_timeout(513, timeout_ms)` with the caller's timeout (vendor default 3000 ms), result never validated, no sleep — `N3R/libtransport_bin/full.asm` 0x174b0-0x1797e, 0x1a200, 0x13ca0; defaults `SDK CPP-SDK/src/DeviceInfo/streamdock.h:133,140`, `SDK Python-SDK/src/StreamDock/Transport/LibUSBHIDAPI.py:664-678`. Report sizes are SDK configuration (`setReportSize(513,1025,0)`, `streamdockN3V25.cpp:39`, `StreamDockN3.py:202`), never read from the device. `transport_set_background_image_stream` rejects only a null handle or zero length.
- **[documented]** Vendor N3 geometry: 320×240 panel, 64×64 keys, key and background rotation 90° (C++ `cv::ROTATE_90_CLOCKWISE`; Python `rotation -90`), i.e. the JPEG sent is 240×320 portrait — `SDK CPP-SDK/src/HotspotDevice/StreamDockN3V25/streamdockN3V25.cpp:45-53`, `SDK Python-SDK/src/StreamDock/Devices/StreamDockN3.py:192-198`. Our probe does the same (`PROBE/burn_logo.py:109-111`). JPEG quality: vendor C++ 85, vendor Python PIL default 75 (baseline, 4:2:0), ajazz 90, Melvin 100 baseline 4:2:0 non-progressive "to match the StreamDock app byte-for-byte in flavour" (`N3R/melvin_n3.py:336-338`). Ours: q90, 4:2:0, baseline.
- **[documented]** Vendor call order: `setBackgroundImgFile(); refresh();` (README §5.1; N3V25 test `N3R/sdk/test.h:281-283` adds `sleep_for(1000 ms)` after refresh). Because the sender thread is FIFO and the LOG read task blocks first, the vendor's STP reaches the wire only after that read returns: up to 3 s after the last chunk when no input arrives — `full.asm` 0x13f27/0x14017/0x14086 (senderLoop). Our 20:10 and 22:49 writes sent STP immediately (`PROBE/burn_logo.py:133-134`, `PROBE/log_test.py:42-43`). The timing warnings in the README apply to old-platform (293) devices only.
- **[documented]** No vendor text gives a JPEG size limit (only the H1 Pro's 5 MiB), a baseline/chroma requirement, a trailing byte beyond the constant 0x01, or a quiet period after the write. Nearest hints: ajazz-sdk's u16 length field (< 64 KiB) and its STP-before-data order with a 1 s ACK wait on AKP03 (`N3R`-verified from https://raw.githubusercontent.com/mishamyrt/ajazz-sdk/main/src/device.rs ), rigor's 293 `LOG + u32be 800*480*3 + 0x01` then raw BGR then STP (`N3R/rigor_streamdock.ts:47,175-197`).
- **[documented]** Vendor forum admin on the N3 (Dec 2025): standalone use impossible "因为设备里是没有存储芯片的" — https://forum.mirabox.net/forum.php?mod=viewthread&tid=22500 . About key configs; reconcilable with a boot image in MCU flash (the VSD logo is stored somewhere).
- **[observed by others]** No implementation has verified LOG on 5548:1001: the vendor product table lacks the ID, the C++ firmware switch matches neither "V3.VSDN3" nor "V3.293N3", mirajazz has no LOG, philler's README keeps N3 background rendering as an open TODO (`N3R/philler/README.md:495`), Melvin uses LOG as a live, STP-refreshed "screen image" on 6603:1002 with no power-cycle statement.
- **[observed by us]** 20:10: 11,139-byte JPEG, 11 chunks, every write accepted, no input report; device kept enumerating (`PROBE/NOTES.md:46-49`). 22:49 (not ~20:40; file stamps `PROBE/log_test.py`, `PROBE/boot-image/test-lime-sent.jpg` 22:49): solid lime 1,830 bytes, brightness 100, STP, 2 s listen, 3 s hold, closed without DC (`PROBE/log_test.py:40-57`). Result not yet reported.
- **[unknown]** Persistence on this clone; whether LOG also paints live; firmware validation of dimensions/size; brightness after power-up.

### Q3 — Interrupted/corrupted flash write? How do vendor tools recover?

- **[documented]** Vendor warning: stream-interface misuse "may cause significant damage to the device, and in severe cases, the device may need to be returned to the factory for firmware reprogramming, for example: Image data out of bounds causing device internal deadlock; Image size/format errors causing write failures" — `SDK CPP-SDK/README.md` "Risks of using stream interface" (lines 284-293); CN "严重的需要返厂重新烧录固件程序".
- **[documented]** N4 (sibling model), Mar 2025: replacing the boot logo via the app "reports failure … and after the failure the device goes black and needs to be powered off and reconnected before it is usable"; admin: "已经在处理，下个版本会修复" — https://forum.mirabox.net/forum.php?mod=viewthread&tid=5703 . So a failed logo write producing a black panel that a power cycle clears is a known, non-bricking symptom on a sibling.
- **[documented]** Firmware recovery exists only for the HSV293 (IAP_Programmer via the app; an interrupted flash leaves the deck "完全没显示，也没有反应") — https://forum.mirabox.net/forum.php?mod=viewthread&tid=22 . N3: "固件更新现在还没有正式开放" (Jul 2024, https://forum.mirabox.net/forum.php?mod=viewthread&tid=1158 ); still no update option Aug 2025 (tid=4949 p.2). Download page has installers only — https://mirabox.net/pages/download . VSD: "Firmware updates can be done through the VSD Craft software" (generic), no N3 guide, no boot-logo recovery doc. The vendor's only boot-image "tool" is uploading another image (tutorial above; SDK = call `setBackgroundImgFile()` again).
- **[inferred]** Our unit is not in the failed-firmware state (it enumerates, answers GET_REPORT, emits key events). LOG writes image data, not firmware; the worst plausible outcome is an empty/undecodable boot slot that shows as black at power-up, which is recoverable by writing another image (N4 precedent). The only wire-timing difference between the vendor path and ours before STP is the missing ≤3 s read-wait; after STP the vendor sleeps 1 s and keeps streaming, we waited 5 s and sent DC. Nothing documents either as a hazard, and the ajazz AKP03 driver sends STP before the data, so STP timing is unlikely to be critical — but that is a different unit.
- **[unknown]** Whether this clone's firmware checks JPEG dimensions/orientation before committing; whether a partial write leaves the slot blank or keeps the old image.

### Q4 — What exactly does libtransport do, and is anything sent on usage 2?

- **[documented, binary]** `transport_set_background_image_stream(handle, jpeg, len, timeout_ms)`: header `CRT\0\0LOG` + u32be len + 0x01 → chunks of 1024 → one read task `hid_read_timeout(513, timeout_ms)` → callback that only prints on success and never validates. No sleep anywhere in the LOG path; the only `nanosleep` in the .so is a fixed 2 s in the shutdown helper (`full.asm` 0x10d10, timespec {2,0} at 0x201f0). Caveat: `reserveRead`'s flag is never released, so a second background upload on the same handle stalls 50 ms and throws (swallowed), with the header and chunks still queued and no trailing read (`full.asm` 0x12a50, 0x12bc0 has no caller) — i.e. the vendor path effectively supports one LOG per opened handle.
- **[documented, binary]** `transport_disconnected` = the single DC frame above; `transport_destroy` = no frames. `transport_sleep` = `CRT\0\0HAN`, `transport_refresh` = `CRT\0\0STP`, `transport_heartbeat` = `CRT\0\0CONNECT`, `transport_wakeup_screen` = `CRT\0\0DIS` (rodata 0x1fc80-0x1fd61).
- **[documented]** Usage 2: libtransport opens exactly one caller-supplied path (`hid_open_path` at 0x1274b, `TransportDevice::open`); the vendor Python filter is `usage_page > 1025 and usage == 1` (`LibUSBHIDAPI.py:1093`), the C++ DeviceManager requires `usage == 1 && usage_page == 65440` (`streamdock.cpp:384`), opendeck-akp03 queries `(65440, 1)` for all 13 devices and its changelog records switching from usage 2 to usage 1 "because Windows gets only that" (`N3R/akp03/CHANGELOG.md:168`). On macOS/Linux hidapi reports both usages with the same path (our enumeration: `PROBE/NOTES.md:9`), so there is no second handle to talk to; nothing in any SDK targets usage 2. The vendor refuses to publish the protocol — https://github.com/MiraboxSpace/StreamDock-Device-SDK/issues/63 .
- **[inferred]** Our probe's frames are byte-equivalent to the vendor's for DIS/LIG/CONNECT/BAT/STP/LOG header/chunks/DC; the one difference that matters is the STP gap after LOG.

## 2. Ranked causes of the black panel after 20:10, with the cheapest test

1. **DC cleared the display and the cleared state persists on this clone (no logo fallback, no reboot).** [inferred from documented "clears all display" + our timeline: only DC-terminated session, only black outcome]. Cheapest test: the user unplugs/replugs with nothing running and reports what the boot shows; any picture (lime, token dots or VSD) proves the panel and boot path are fine and the black was the DC state. Host-only alternative: handshake + one bright BAT tile + STP (no LOG) — tile visible ⇒ the panel paints after DC. Killed only if a replug also shows black with no VSD (then cause 2 is live).
2. **The 20:10 LOG left the boot slot blank or unrenderable on this VSD firmware** (orientation/size/flavour not accepted, or write not committed). [inferred; N4 forum precedent documented]. Test: the replug after the lime write. Black + no VSD ⇒ confirmed (our LOG framing or encoding fails here, or the slot is damaged); lime ⇒ killed; VSD ⇒ cause 4.
3. **STP 0 ms after the last chunk (vendor: up to 3 s) and/or DC 5 s later interrupted the ROM write.** [inferred; undocumented]. The 22:49 lime write repeated the immediate STP but not the DC. Lime after replug ⇒ killed outright. Black ⇒ redo one LOG with the vendor rhythm: write, read with a 3 s timeout, STP, ≥1 s, keep CONNECT every 10 s for ≥10 s, close without DC, then replug.
4. **LOG was ignored/rejected (boot slot still VSD); black is purely the DC state.** [inferred]. Test: replug shows VSD ⇒ confirmed; burning a welcome screen via this LOG framing is then not available.
5. **The dark token field is displayed and reads as black.** [largely refuted]: the sent image has 53 squares, every 3×2 window arrangement exposes ≥10 of them at luma ≥195 (`PROBE/boot-image/boot-image-sent.jpg`, `PROBE/burn_logo.py:87-100`); "100% empty" does not fit. Moot once the lime write is judged.
6. **Repaint stall / wedge** (Melvin's V3.293N3 "stops repainting", issue #103's drop-off). [observed by others on sibling firmware]. Keys work and the device enumerates, so not a full wedge. Replug fixes it if so.
7. **Backlight off.** [inferred, weak]: DC is not documented to touch the backlight; LIG 70 was sent. Test: look for a glow in a dark room; host sends DIS + LIG 100.

What the user's next look at the lime write means (look now, again after ~2 min idle, then after unplug/replug):

| Now (connected session already closed, no DC) | After replug | Implication | Next step |
|---|---|---|---|
| lime | lime | LOG paints live and persists in ROM; our framing/encoding is right; 20:10's black was the DC clear (cause 1) | burn the welcome once; quit without DC (section 3) |
| lime | VSD | LOG is a volatile live background on this firmware; boot logo separate and intact | no burn via LOG; app paints welcome tiles at quit; VSD stays at boot |
| lime | black, no VSD | live path works, the ROM copy failed (cause 2/3) | rewrite with vendor rhythm (3 s wait before STP, 1 s after, heartbeat, no DC), replug; then q85 and `--landscape` variants one at a time, replug each |
| black | lime | LOG goes only to the boot slot, not the live panel | burn; app must paint tiles on every connect |
| black | VSD | LOG never took (cause 4) | if lime never appeared live either, LOG is dead on this firmware with this framing |
| black | black, no VSD | slot blank/corrupt, or panel not painting at all | first prove painting: handshake + bright BAT tile + STP; if the tile shows, redo LOG with variants; if not, hardware/wedge → VSD/TreasLin support |
| lime now, then switches by itself to another picture within ~2 min | — | the firmware reboots/falls back on host silence (the #44 mechanism); what it switches to is the boot slot content | that picture is the answer to the replug column |

## 3. What the Token Deck app should do

First connect (every launch):
1. Open the vendor collection (VID 0x5548/0x6603, usage page 0xFFA0, usage 1; on macOS usage 2 is the same path), non-exclusive; 1025-byte output reports with report-ID 0; 512-byte input reads (`PROBE/NOTES.md:9-11`, `PROBE/burn_logo.py:45-49`).
2. Handshake exactly as the vendor app: `DIS`, `LIG <pct>`, `QUCMD 1f 11 00 11 00 11 00`, `LIG <pct>` — input reports arrive only after it (`PROBE/NOTES.md:12-13, 22-23`).
3. `CONNECT` every 10 s for the whole session (vendor frame; without it the N3 reboots about every minute — opendeck-akp03 #44/#45).
4. Paint the UI tiles with `BAT` + `STP` (verified on this unit, `PROBE/NOTES.md:20-21`). Keep traffic flowing while connected (a periodic STP or tile refresh every few seconds): the vendor app re-uploads a key image + refresh every second and Melvin's daemon copies that because V3 firmware "stops repainting after a period of silence" (`N3R/melvin_README.md:39-41`; observed on 6603:1002, not yet on this clone).
5. Burn the welcome screen only when both hold: (a) the lime test proved LOG persists through a replug on this unit (table rows 1 or 4), and (b) the welcome image hash differs from the hash stored for this serial. Never on every launch: the vendor calls it a ROM write, "slower", and its own transport can do one background upload per handle.

Burn procedure (vendor-equivalent wire sequence; everything here is in `PROBE/burn_logo.py` except the 3 s gap):
- Encode: 320×240 landscape → rotate 90° clockwise (PIL `rotate(-90, expand=True)`) → 240×320 → JPEG baseline JFIF, 4:2:0, non-progressive. Quality 85 (vendor C++) or our q90 (accepted); keep the file small (ours: 11,139 B fine; no documented limit; ajazz's u16 field implies < 64 KiB).
- Send `CRT\0\0LOG` + u32be len + `0x01`, then the 1024-byte chunks. Then read input with a 3 s timeout (expect nothing on this unit; this reproduces libtransport's gap). Then `STP`. Then ≥1 s before any other frame (vendor N3 test). Keep the heartbeat running and the handle open for at least another 10 s. No `DC`, no `HAN`, no close inside that window.
- Abort rule: if any `hid_write` fails mid-stream, do not send `STP`; drop the session, let the user replug, and resend the whole stream after a fresh handshake (vendor: out-of-bounds/partial image data can deadlock the device).
- One burn per session. Verification is by eye only (no read-back API): tell the user to unplug/replug and confirm.

Quit (goal: deck shows the welcome screen):
- Paint the welcome screen's six 64×64 window crops as `BAT` tiles + `STP`, stop the heartbeat, close the handle. Send **no `CLE DC`** (documented "clears all display"; the only DC-terminated session on this unit ended black; no source shows a logo fallback on this clone) and **no `HAN`** (sleep = dark panel; it is how mirajazz blanks the screen after DC).
- Expected result either way: the panel holds the last-written tiles when the host stops (issue #103 saw exactly that on this clone — https://github.com/MiraboxSpace/StreamDock-Device-SDK/issues/103 ), and if the firmware reboots on host silence (#44; our early sessions ended on the boot logo) it comes up on the burned welcome image: same picture. A crash is identical to this path (nothing is sent).
- Keep DC behind a debug flag. Run one controlled test later, when the welcome is burned and verified and the user can replug: handshake, DC, close (`PROBE/burn_logo.py --dc-only` logic). If DC turns out to show the boot image on this clone, it becomes the cleaner quit; if it shows black again, the flag stays off for good.

## 4. Open risks and what the vendor says not to do

- **Vendor must-nots** [documented]: wrong/out-of-bounds stream data can cause "device internal deadlock" or write failures and in severe cases factory reprogramming (`SDK CPP-SDK/README.md:284-293`); a boot logo with the wrong resolution makes the upload fail or the progress bar stick (Mirabox tutorial). Practical rules: validate 240×320 after rotation and JPEG baseline before every LOG, never send a partial stream or two streams at once, and make sure VSD Craft is not running (two writers).
- **If the slot is blank/corrupt** (replug shows black, no VSD): the only recovery mechanism anyone documents is writing another image (app "Replace the boot logo" = `setBackgroundImgFile()`); the N4 precedent needed a power-off + reconnect to become usable first (tid=5703). Try the vendor rhythm first, then one variable at a time (q85; `--landscape` 320×240; smaller file). No firmware or boot-image recovery tool exists for the N3; if the unit ever stops enumerating, the only route is TreasLin/VSD support (HSV293 precedent: IAP tool or return to factory).
- **The factory VSD logo is gone unless a copy exists** [documented + our note]: vendor reset does not restore the default logo and no restore function is documented; we never captured it (`PROBE/NOTES.md:56`). Unknown and worth a read-only look if the user cares: whether the VSD Craft app bundle ships a default boot-logo asset.
- **This exact clone drops off USB intermittently** and needs a physical reseat (#103, same firmware string): the app must tolerate `IOHIDDeviceSetReport … device not responding`, never block the UI on a write, re-enumerate and repaint. Burn only right after a fresh connect, when the bus is quiet.
- **Missing keep-alive = reboot loop** (#44): tiles vanish on each reboot; the app must repaint after re-enumeration and must never pause CONNECT during a burn.
- **Unknowns that the plan already tolerates**: whether LOG also paints live; brightness after power-up (whether LIG persists); the JPEG size limit; whether the clone validates image dimensions; whether DC ever shows the boot image here.
- **Fix our own notes**: `PROBE/NOTES.md:17` ("CLE\0\0DC … the device falls back to its stored logo") and `PROBE/burn_logo.py:138` comment are unverified assumptions; the only documented effect is "clears all display", and the 20:10 observation points the other way. `PROBE/NOTES.md:54-56` should also record the 22:49 lime test and its result.
- **Second HID collection**: nothing to do; no SDK or driver uses usage 2, and on macOS it is the same handle.
